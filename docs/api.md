# API

Read before: adding or changing a route, a status code, or a query parameter.

Every `/api/*` route needs a credential under `AUTH_MODE=github`, and none under `AUTH_MODE=none`.
Which one each takes is in the table in [auth.md](auth.md); the exemptions worth knowing here are
`GET /api/health` and `/api/auth/*`, and the fact that the SPA's own document is never gated. An
unauthenticated `/api/*` request is `401 UNAUTHENTICATED` — the one exception is `GET /api/auth/me`,
whose anonymous answer is `200 {authenticated: false}` (see its row). On the session routes a
`Bearer fat_…` / `oat_…` access token is an alternative to the cookie — and when both arrive the
bearer wins ([auth.md](auth.md)).

| Route | Behaviour |
| --- | --- |
| `GET /api/auth/github` | `302` to GitHub, setting a signed, single-use state cookie. `?returnTo=` is validated as a same-origin absolute path; anything else becomes `/`. `?org=` (a deep link's preferred organization) rides the signed state and is only a preference — the callback validates it against the installations GitHub reports. `?reselect=1` asks the callback to re-open the selection screen even though the account already has a stored choice (#125) — the only surface for changing the choice, because the token that enumerated the installations is discarded at sign-in. |
| `GET /api/auth/github/callback` | `302` on every outcome, never JSON — it is reached by a top-level navigation, and an error body is a dead end for the human in front of it. Failures carry `?auth_error=denied\|state\|github\|install`; `install_cancelled` is set by the setup route. Success has three outcomes (#125): zero installations redirects to GitHub's install page; one installation — or a stored selection intersected with the report — signs straight in; a first sign-in with two or more (or `?reselect=1` with two or more) parks the identity and report in a single-use `pending_sign_in` row, sets the pending cookie, and redirects to `/onboarding`. |
| `GET /api/auth/github/pending` | `200 { identity, installations, selected, reselect, org, returnTo }` — what the onboarding screen renders for the parked sign-in (#125); `selected` is the stored choice when there is one (a reselect) and every reported installation otherwise. `401 NO_PENDING` without a live pending cookie — the one "start again" answer for missing, forged and expired alike. |
| `GET /api/auth/github/pending/installations/:installationId/repos` | `200 { repos, source }` — one installation's repositories as `owner/name`, listed through a transient App client because the org rows this choice is deciding on do not exist yet (#125). `source: 'none'` means there was nothing to ask (offline, or GitHub failed); narrowing such an org is refused at completion, never guessed. `400 UNKNOWN_INSTALLATION` for an id the parked report does not name. |
| `POST /api/auth/github/complete` | `200 { organization, returnTo }` — materializes the posted selection (`{ orgs, repos? }`) and finishes the parked sign-in (#125). JSON errors, not `?auth_error=` redirects — the SPA's fetch reaches it, not a navigation. `401 NO_PENDING` for a missing or spent pending row (single-use); `400 BAD_SELECTION` for an empty, duplicated, non-reported or repos-key-mismatched selection; `400 REPOS_UNAVAILABLE` for narrowing an org whose repos cannot be listed; `400 UNKNOWN_REPO` for a name outside the installation's listing. |
| `GET /api/auth/github/setup` | `302`. The GitHub App's **Setup URL** target (operator-configured in the App settings). An install return (`installation_id` present) restarts the sign-in with that organization preferred and `reselect=1`, so an existing choice cannot hide the new installation; arriving without one means the person returned without installing, and the redirect reports `?auth_error=install_cancelled`. |
| `POST /api/auth/org` | `200 { organization }` — moves the session to `body.orgId`, only when the caller is a member of it (`403 FORBIDDEN` when not, `400 UNKNOWN_ORG` when no such org, `400 BAD_ORG` without an orgId, `401` anonymous, `400 NO_SESSION` without a session cookie). Every subsequent read resolves through the new org. |
| `POST /api/auth/logout` | `204`, including for a caller who was never signed in. POST because a GET logout is CSRF-able and gets fired by link prefetchers. |
| `GET /api/auth/me` | `200 { authenticated: false }` for an anonymous caller, else `200 { authenticated: true, user, role, membership, account, organization, organizations, workspacePath, mode }` — `organization` is the session's own org and `organizations` every one the account could switch to (the selector's data). Never a 401: the browser logs every 4xx as a console error even when the client handles it, and the login screen must open without red devtools rows. `user` carries `id`, `login`, `name`, `githubUserId`, `avatarUrl`; `membership` carries `invitedAt`/`claimedAt` and `account` carries `createdAt`/`lastLoginAt`, all ISO 8601 or null. `workspacePath` is the member's checkout root, null when no workspace root is configured; computing it provisions nothing. Under `AUTH_MODE=none` the caller is the stand-in account (`login` `__local__`, `githubUserId` 0, `avatarUrl` null) — facts, not display hints. Deliberately exempt from the wall: being what *tells* the SPA it is unauthenticated is its whole purpose. |
| `POST /api/tokens` | `201 { id, token }` — `token` is the plaintext `fat_…`, in this one response only; the row holds its sha-256 and nothing can read it back. `400 BAD_LABEL` on a missing, blank, or over-128-character label. |
| `GET /api/tokens` | `200 { tokens }` — the caller's own personal tokens as `{ id, label, createdAt, lastUsedAt, revokedAt }`. Never a token or a hash: the list answers "what tokens exist", not "who can use them". |
| `POST /api/tokens/:id/revoke` | `200 { id, revoked: true }`. `404 NOT_FOUND` when the id is unknown, somebody else's, or already revoked — a revoke that changed nothing has no row to name. `400 BAD_ID` on a non-uuid. |
| `POST /api/tokens/org` | `201 { id, token }` with an `oat_…` organization token, mintable by any member — installation access is one trust level (#99). The token acts for the organization on read-only routes and has no user; same `BAD_LABEL` rules. |
| `GET /api/tokens/org` | `200 { tokens }` — the org-wide list, same shape. |
| `POST /api/tokens/org/:id/revoke` | `200 { id, revoked: true }`. `404 NOT_FOUND` / `400 BAD_ID` exactly as the personal revoke. |
| `GET /api/health` | Never calls GitHub or the database. A container whose migrations are still retrying is up and answering, so probing either here would fail the compose healthcheck and restart the container that was about to succeed. |
| `GET /api/stats` | `200` with `{ telemetry, tasks, meta }`, where `telemetry` is `TelemetryStats \| null`, `tasks` is the per-task usage distributions (`{ tokensPerTask, jobTurnsPerTask, agentTurnsPerTask, wallClockPerTask }`, each `{ avg, p50, p95, tasks }` — nearest-rank percentiles, null when nothing was measured) over the same range and scope, and `meta` is `{ fetchedAt, ageSeconds, stale, organization, repos, range, scope, scopeLogin, telemetry }` — the inner `meta.telemetry` carries the read's own state (`ok`/`empty` — `disabled` and a failed first read answer `503` instead — plus `source`, `otherRepoSessions`, `sessionsWithoutHook`, `unattributedSessions`). The figures are the caller's org's own — `meta.organization` names which (see [repos.md](repos.md)). `telemetry.byUser` is the per-user rollup over in-scope sessions (each row `{ user: { id, login, name, avatarUrl }, sessions, tokens }`), resolved by joining the telemetry rows to the job audit rows on session id at read time — the telemetry tables themselves carry no identity; `telemetry.unattributedSessions` counts in-scope sessions with no matching task (a local dev run, a backfilled transcript), named rather than hidden. `telemetry.series` is the usage series as `{ granularity: 'day' \| 'week', points }` — day buckets up to a 92-day window, ISO weeks beyond, the payload naming the granularity the chart renders. `telemetry.totals.editAcceptance` reports the edit-acceptance measurement as `{ accepted, rejected, decisions, ratio }` — `decisions` is the measured denominator (the null-aware sum of accepted and rejected), null means unmeasured while a measured `0` renders as `0`, and `ratio` is null when the numerator was unmeasured or no decisions were measured, else within [0, 1]; no comparable-window/delta contract exists on these fields. `202` with progress while the first read runs (SPA polls every 2s); `503` with `TELEMETRY_DISABLED` when `TELEMETRY_SOURCE=off` — with nothing else in the payload, because telemetry is the whole payload — or with the failure when the first read failed cold. A stale cache is still a 200: a failed read must keep the last good render on screen and explain itself, not blank the dashboard. `?range=day\|week\|2w\|month\|all\|custom` (default `all`), plus `?from=&to=` for `custom`; `400 BAD_RANGE` on anything unparseable, never a silent fallback to all time. `?scope=org\|mine` (default `org`): `mine` scopes every figure to the signed-in caller — resolved from the session or a personal token, named in `meta.scopeLogin`; `400 SCOPE_REQUIRES_USER` when the request carries no person (open auth mode, or an organization token, which names nobody) rather than silently serving org figures under a personal heading; `400 BAD_SCOPE` on any other value. A scope switch re-aggregates the cached snapshot — it never re-fetches. `?org=` asks for a different organization the caller belongs to: unknown is `400 UNKNOWN_ORG`, known-but-not-theirs is `403 FORBIDDEN`; `meta.organization` reports `{ mode, current, available }` — `mode: 'directory'` when sign-in materialized the orgs, `'config'` under open auth. |
| `POST /api/otlp/v1/metrics` | `200 {"partialSuccess":{}}`. 1 MB limit, JSON only. Registered only when a store exists. |
| `POST /api/otlp/v1/logs` | `200`. Accepted and dropped — see M6 in the plan. |
| `POST /api/sessions/branch` | `202`. Needs an org-bound credential in github mode — the runner's attempt pair (`x-factory-job-id` + `x-factory-job-lease-token`, the claim's lease) or a personal `Bearer fat_…`; **`401 UNAUTHENTICATED`** with neither or a pair that resolves to no live attempt. `400` on a malformed body — checked *after* the credential, so an unauthenticated caller learns nothing; `503` only when the write fails. The report's organization is the credential's, never the `repo` field's (see [auth.md](auth.md)). Under `AUTH_MODE=none` it is open. |
| `POST /api/jobs` | `201 { id, status }`. `400 BAD_COMMAND` on a missing, empty or over-16-KiB command — the cap applies to the RAW command and again to the built one a resolved workflow's entry prompt interpolates into. Optional `repo` (`owner/name`, both segments path-segment-safe, ≤100 characters each — `400 BAD_REPO`) and `executor` (path-segment-safe — `400 BAD_EXECUTOR`) are stamped as audit labels and validated by shape only, never against the member's mutable `user_repo` / `user_executor` rows. At claim, the executor label resolves in the AUTHOR's current profiles and its type selects Claude Code or OpenCode; absent or unresolved, the driver fails the task rather than choosing a deployment default — see [jobs.md](jobs.md). The composer therefore requires a configured executor. The repository name is additionally checked against the caller's org's installation list: **`400 UNKNOWN_REPO`** for one it cannot see — the clone would only 404 (see [repos.md](repos.md)). Optional `workflow` names the definition the task walks, resolved within the caller's visible scopes, repo over user over org (`404 UNKNOWN_WORKFLOW`, `400 BAD_WORKFLOW`, see [workflows.md](workflows.md)); a `defaultWorkflow` field alongside it is always **`400 BAD_DEFAULT_WORKFLOW`**, before the name is ever resolved. Unnamed, the task walks the code-owned DEFAULT workflow instead (issue #209) — never a member-authored row: `defaultWorkflow` may name a complete `{ reviewReconciliation, mergeConflictAutofix }` boolean pair as a one-task override (missing, extra or non-boolean keys are **`400 BAD_DEFAULT_WORKFLOW`**, no row inserted); absent, the caller's saved settings (`GET`/`PUT /api/workflows/default-settings` below) decide, and a missing row or no signed-in caller means both steps on. When a workflow resolves (named or the default), the body may carry `workflowParams` — one value per parameter the definition DECLARES; every declared parameter is required, values trimmed non-empty strings ≤512 characters, full-matched against the declared pattern — and the ROOT command becomes the interpolated ENTRY prompt, not the raw chat line. **`400 BAD_WORKFLOW_PARAMS`** for a missing, malformed or unexpected parameter value; the default workflow declares none, so any `workflowParams` sent beside an unnamed task is this same refusal. The resolved record's NAME is stamped on the task as `workflowName` (`'default'` for the code-owned one) — frozen at create, inherited by every turn of the thread; like `created_by`, it comes from the record the store resolved, and no body field can supply or override it. Records `created_by` from the authenticated caller, **never from the body** — a client-supplied author is impersonation on the audit trail of a route that runs shell commands. |
| `POST /api/jobs/claim` | `200 { id, command, attempts, leaseToken, leaseExpiresAt, userId, workspacePath, rootJobId, resumeSessionId, followUp, env, repo, gates, gateError }`, or **`204`** when nothing is waiting — an idle poll is the common case and must be recognisable without parsing a body. `resumeSessionId` is non-null only when the claim is running a follow-up, which resumes the parent's session, and the worker restores that session instead of starting one. `followUp` is true only when that resumed session should ALSO receive the command — a follow-up's first or crashed attempt. `userId` is the account that queued the job, or null for one queued before accounts existed; it is still shipped ahead of its remaining consumer, the per-user Claude credential. `workspacePath` is the author's checkout directory **relative to the workspace root** (`<orgId>/<userId>`), or null when the job has no author or the board has no workspace root — the driver **fails** such a job rather than falling back, because every broader path is the parent of somebody else's tree. `rootJobId` is the thread's root job id — the job itself, or the chain's first job for a follow-up — the key the task worktree is filed under (`docs/jobs.md`), so every attempt and follow-up of one task lands in the same tree; the claim enforces that one-thread-one-claim too, refusing a row whose root already has a `running` row, so a queued follow-up waits (as `204` for that worker) until the row it follows reaches a terminal status. `env` is the stacked runner environment (org < workspace < repo) resolved for this job's author and repo label — present only when the board was built with an env store, and never persisted on the job row. `repo` repeats the job's `owner/name` label (the checkout the gates live in); `gates` carries the checkout's parsed `.bellows.yaml` (`{ image, gates: [{ name, command }] }`) read off the server's workspace mount at claim time, or null when the repository declares none; `gateError` names why a file that exists could not be honoured — the driver fails such a job with the reason before running anything. All three are absent on a board that predates gates. `400 BAD_WORKER` / `BAD_LEASE`. |
| `POST /api/jobs/:id/heartbeat` | `200 { leaseExpiresAt, cancelRequested }`. **`409 LEASE_LOST`** once the lease has been reclaimed — the driver kills the container on this, and it is the only signal a superseded worker gets. `cancelRequested` is the stop channel: a user's `/stop` stamped the row, and this beat is the worker reading that it must park — it kills its runner and calls `/suspend`. False on every ordinary beat, and false on `lost`/`404` (a lost lease tells the worker nothing about a stop the next worker will land on). `404` unknown, `400 BAD_ID` / `BAD_TOKEN` / `BAD_LEASE`. |
| `POST /api/jobs/:id/session` | `200 { id, sessionId }`. Records the agent session the running attempt is using: `sessionId` is a bounded opaque token — a claude uuid, known at spawn, or opencode's `ses_…`, which the runner scrapes out of the run's session database and reports at close, before the verdict. Lease-guarded: `409 LEASE_LOST`, `404`, `400 BAD_ID` / `BAD_TOKEN` / `BAD_SESSION_ID`. Separate from `complete` so the session is on the row while the job is still running. |
| `POST /api/jobs/:id/output` | `200 { id }`. A rolling tail of the running attempt's output, streamed while it runs so the dashboard shows the work instead of a spinner. The **driver owns the window** — it sends its newest tail at most every couple of seconds, and the board stores that tail **replacing** the previous one, never appending (an unbounded append would grow the row for as long as a session runs). An optional `runtime` object rides beside the tail — the driver's latest sample of the runner container (`cpuPercent`, `memUsedMb` — null when not read this round, so a cluster with no metrics-server still reports its fleet — `memPercent`, `activity` — the agent's current output line — `sampledAt`) plus the attempt's declared `.bellows.yaml` services as `services` (`[{ name, image, state }]`, lowercase platform-native states, at most ten; omitted entirely when the attempt declared none). The task view's "is it stuck or working" answer; absent means no sample this round, and the last stored one stays — the object is merged key-wise, so a report without `services` keeps the stored fleet and null numbers keep the last good numbers. The final `complete` report overwrites the tail; the last sample stays on the finished row, where "was it doing anything when it died" reads off `sampledAt`. The final `complete` report overwrites the tail; the last sample stays on the finished row, where "was it doing anything when it died" reads off `sampledAt`. Lease-guarded like every worker write: `409 LEASE_LOST` — which, unlike on `heartbeat`, is **not** a kill order, because the heartbeat is the one place that decides a superseded run must die. `404`, `400 BAD_ID` / `BAD_TOKEN` / `BAD_OUTPUT` / `BAD_RUNTIME`. |
| `POST /api/jobs/:id/gates` | `200 { id }`. Replaces the run's gate state — the checks the job's checkout declared in `.bellows.yaml`, executed by the driver in the declared environment image. Body `{ leaseToken, gates: [{ name, status: 'running'\|'passed'\|'failed', exitCode, output }] }`; the stored list is **replaced**, never appended, which is what makes the task view's current/last-only honest. Per-gate `output` is truncated to 64 KiB server side. Lease-guarded like every worker write: `409 LEASE_LOST` — not a kill order, the heartbeat decides that — `404`, `400 BAD_ID` / `BAD_TOKEN` / `BAD_GATES`. |
| `POST /api/jobs/:id/gates-reread` | `200 { gates, gateError }`. Re-reads the checkout's `.bellows.yaml` after the driver's startup sync has landed the worktree — the claim's answer was read before the sync and can be stale. Lease-guarded: `409 LEASE_LOST`, `404`, `400 BAD_ID` / `BAD_TOKEN`. |
| `POST /api/jobs/:id/publish-token` | `200 { GITHUB_TOKEN }` — the credential to push the run's work with, fresh enough for the push: the claim's installation token is minted at claim time with an hour on it, and a run can outlive that (job 43379d3a: a 1h33m run's publish died on its expired claim token with the work done and the gates green). The answer re-runs the claim's environment assembly NOW — an operator-configured `GITHUB_TOKEN` wins exactly as at claim time, the mint (when there is one) is fresh, and a **null `GITHUB_TOKEN` is an answer, not an error**: nothing fresher than the claim env, publish with what you hold. Lease-guarded like every worker route: `409 LEASE_LOST`, `404`, `400 BAD_ID` / `BAD_TOKEN`. |
| `POST /api/jobs/:id/suspend` | `200 { id, status }` with the landed status: `stopped` — the park is the user's stop landing, the row is terminal, the turn ended, its `sessionId` kept for the follow-up that continues the conversation. The attempt is handed back to the claim. `409 LEASE_LOST`, `404`, `400 BAD_ID` / `BAD_TOKEN`. |
| `POST /api/jobs/:id/stop` | `200 { id, status: 'stopped' }` — the turn is over (queued rows and running rows whose lease has already expired — nobody holds the lease, so there is nobody left to deliver to — answer this directly) — or `202 { id, status: 'running', cancelRequestedAt }` when the stop landed on a moving run under a live lease and the driver has not settled it yet. **Takes no lease token**, and idempotent while the run is still going: a running one already stamped answers the same `cancelRequestedAt`. The acting caller is recorded as `stopped_by` (025) at the request, first asker wins. The board cannot stop a worker — the request rides the heartbeat the worker already sends, and the worker settles via `suspend`, which lands `stopped` (`cancel_requested_at` is cleared when the parking or the finishing lands, never by the request itself). A run whose worker died mid-stop is never re-claimed: the claim settles the stamped row `stopped` (#152), keeping the session the follow-up continues. The session is kept either way: the follow-up composer is what the member sees next. `409 NOT_STOPPABLE` for a task that already ended (named with its `status`), `404` unknown, `400 BAD_ID`. |
| `POST /api/jobs/:id/follow-up` | `201 { id, status: 'queued' }`. Queues an adjustment on a **finished** task — `succeeded`, `failed`, `dead`, or the user's own `stopped` — as a continuation of the run it just did: the new job inherits the parent's `repo`, `executor` **and** agent session, and the claim arrives at the driver with `followUp: true` so the command is delivered **into** the restored transcript (`--resume <id> -p <command>`, or opencode's `run --session <id> <command>`). Body `{ command }` — nothing else is taken from it: `repo` and `executor` are copied from the parent at insert, because an adjustment continues the run it adjusts, on the executor that ran it; a stale `executor` in the body is ignored, never an error. `createdBy` from the authenticated caller, never the body. Author-scoped: only the account that queued the task may follow it up, because the follow-up resumes the parent's session and a session only resumes in the checkout tree it ran in. Refusals are decided atomically with the insert: `404` unknown parent, `409 NOT_FINISHED` (queued/running), `409 TASK_DONE` (the user has closed the task), `409 NO_SESSION` (nothing to continue — a run that never reported a session: tasks queued before the session mechanic existed, or a run whose driver died before reporting), `403 FORBIDDEN` (queued by another account). `400 BAD_ID` / `BAD_COMMAND`. |
| `POST /api/jobs/:id/done` | `200 { id, status, doneAt }`. The user's verdict that the task is done — the one no run can make. **Takes no lease token**: it is a person's action on a task no worker holds. Terminal tasks only, and idempotent — a second call answers the same `doneAt`. The acting caller is recorded as `done_by` (025) beside the stamp, first writer wins. Done is what frees the task worktree: when the whole thread is already terminal the same transaction queues a `task_reclaim` row for it (a thread still moving waits — its last completing verdict reclaims, see `complete`). `409 NOT_FINISHED` for a task that is still queued, running or parked, `404` unknown, `400 BAD_ID`. |
| `POST /api/jobs/:id/remove` | `200 { id, removed: true }`. Deletes the **whole thread** — the task's root and every follow-up — and inserts a `task_reclaim` row for a driver to remove the worktree, one transaction under the same advisory lock the claim takes (`docs/jobs.md`), so a live claim cannot slip a `running` row between the check and the delete. The acting caller rides the `task_reclaim` row as `removed_by` (025) — the thread rows themselves are deleted in the same transaction, so the reclaim row is the removal's only surviving artifact. **`409 TASK_RUNNING` while any member of the thread is running — stop it first.** Takes no lease token. `404` unknown, `400 BAD_ID`. |
| `POST /api/jobs/:id/complete` | `200 { id, status, threadDone }`. `threadDone` is the store's answer, computed in the same transaction as the verdict, to whether EVERY job of the job's thread (root and follow-ups) is terminal AND one member carries the user's `done_at` — the driver's worktree-reclaim signal (issue #47), riding the lease-guarded complete rather than a thread read so a worker credential never pulls audit data of jobs it does not hold. A thread that merely finished keeps its tree; the done that lands on an already-terminal thread queues the reclaim itself (see `done`). `409 LEASE_LOST` for a report from a worker that no longer holds the job; refused, never merged. `404` unknown; `400` on a status outside `succeeded\|failed`. Optional `contextTokens` (integer 0..10⁸) and `contextCostUsd` (number 0..10⁶) — the context the run reached and what it cost, scraped by an opencode runner from the session database at close — ride beside the verdict and merge into the `runtime` vitals, creating them when no container sample ever landed; `400 BAD_CONTEXT` when out of bounds, and both absent stores nothing. Optional `agentTurns` (integer 0..2 147 483 647 — the column is int4, and an out-of-range value would fail the verdict's transaction; `400 BAD_AGENT_TURNS` otherwise) — the job's agent turns, one assistant response cycle per count in the run's ROOT conversation, counted at close from the session's own records by either executor (see docs/jobs.md and the terminology block in docs/metrics.md). Absent stores null: null is UNMEASURED, never zero — a genuine zero-response run reports 0. Optional `summary` — what the run did, in the agent's own last words, lifted by the same close-time read; truncated to 512 characters server side (`400 BAD_SUMMARY` on a non-string), and absent, null or empty all store null — null is unmeasured, never an empty string. Optional `publication` (036) — the PR identity a real publish landed: `{ repo, prNumber, prUrl, headBranch, baseBranch }`, validated by shape in the route (`400 BAD_PUBLICATION` on anything malformed) and cross-checked against the leased job's own `repo` label inside the verdict's transaction before it is recorded (`job_pr`). A successful publish reports it so the thread is anchored to its PR; a no-op or failed publish reports nothing and records nothing. `output` is truncated to 64 KiB server side. |
| `POST /api/reclaims/claim` | `200 { id, rootJobId, repo, workspacePath, leaseExpiresAt }` — a parked worktree waiting for removal (a thread somebody `remove`d, or one whose done landed on an already-terminal thread) — or **`204`** when the queue is empty, the same idle-poll shape as the job claim. Body `{ worker, leaseSeconds }`: the worker name is required and the row is queued for exactly the worker that claims it. The row **id IS the lease token** — `ack` names the row and the store matches `claimed_by` on it, so there is no token to lose. `400 BAD_WORKER` / `BAD_LEASE`. |
| `POST /api/reclaims/:id/ack` | `200 { id }`. The worktree is gone; the reclaim row is deleted. Only the worker that holds the claim may ack it — `409 LEASE_LOST` when a faster worker re-claimed the row (the worktree still has to come down, so the loser retries) — `404` unknown, `400 BAD_ID` / `BAD_WORKER`. |
| `GET /api/jobs/:id` | `200` the job, `404` otherwise. `createdBy` names the account that queued it, or null. `author` is that account resolved at read time (`{ id, login, name, avatarUrl }` — the display labels, never denormalised onto the row; null for a pre-accounts row, rendered "unknown" by the UI). `stoppedBy` and `doneBy` resolve the stop and done verdicts' actors the same way (025; stamped at the action, first writer wins). `repo` and `executor` carry the labels the task was queued with, or null for one queued before the tasks chat. `gates` carries the run's current/last checks (the driver's reports to the gates route), or null for any run whose repository declares none. `followUpTo` names the finished task this job continues, or null; `rootJobId` names the thread's root task — the job itself, or the conversation's first run — so any turn resolves to its whole task without climbing parents. `doneAt` carries the user's done verdict, or null until they say so. `cancelRequestedAt` stamps when a stop was requested on this running row and the driver has not parked it yet, or null. `sessionId` is null until the driver reports it, and again from the moment the job is re-claimed for a *new* attempt — it survives a park, and a follow-up carries a copy from the moment it is created. `workspacePath` is the author's checkout directory relative to the workspace root (`<orgId>/<userId>`), the same field the claim carries, derived here for the task view's status sidebar — null when the job has no author or the board has no workspace root. `workflowNode` is this row's graph position, null off-graph (workflow-less rows, user follow-ups). `workflowName` is the workflow the thread was launched under — the name frozen at create (033), inherited by every turn, never rewritten by a later rename or delete of the source workflow, and null on workflow-less tasks and unrecoverable history; distinct from `workflowNode`. The thread route serves the same shape. |
| `GET /api/jobs/:id/thread` | `200 { jobs }` — the whole follow-up chain containing this task, oldest first. **Any member's id resolves to the same conversation** (every member carries the thread's `rootJobId`, and the read collects everyone who shares it), which is what lets the UI render one task per thread while follow-ups stay new rows on the board. `404` unknown, `400 BAD_ID`. |
| `GET /api/jobs` | `200 { jobs }`. `?status=&limit=&repo=` (default limit 50, cap 200). `?status=` takes any one status, or **`terminal`** — every settled verdict at once (`succeeded`/`failed`/`dead`/`stopped`), grouped as **one row per task, not per run** (#124): the terminal rows fold by `root_job_id`, so a finished conversation with follow-ups appears once. Identity fields are the ROOT's (`id`, `command`, `author`, `createdAt`, `workflowName` — the thread's frozen name, 033); present-tense fields are the chain head's — the newest member, the sidenav's `chainHead` rule (`status`, `summary`, `runtime`, `sessionId`, `startedAt`); the wall clock is the thread's banked total (`taskWallClockMs`, the figure the task view's head clock renders — the head run's own clock rides `wallClockMs`) and `finishedAt` is the thread's max; `doneAt`/`doneBy` come from whichever member carries the thread's done, and `stoppedBy` follows the head — the row's verdict is the head's. A thread with a member still queued, running or parked is not completed and is excluded whole; ordering is by the thread's newest completion and the limit bounds TASKS, not runs. The per-run lists (no status, one named status) stay one row per run — the tasks pages and sidenav group on the client. `?repo=` is an exact match under the same `BAD_REPO` rules as create; jobs queued before the column existed have `repo: null` and appear only in unfiltered lists. Follow-ups inherit the parent's `repo`, so a thread reads as one conversation under one repository. `output` and `gates` are omitted from the list projection — `output` is unbounded and no list view shows it, and gate state is current/last detail the task view alone renders. `runtime` is not omitted: a vitals object is a few hundred bytes where `output` is an unbounded tail, and the nav and task view render `runtime.activity` as a task's live summary (issue #61). `summary` (the close-time agent summary, ≤512 characters, null unmeasured — the HEAD run's on grouped rows) and `wallClockMs` ride the list projection for the recently-completed view (#109, #124). `workspacePath` and `cancelRequestedAt` are derived for list rows exactly as for the detail, and so is authorship: `author` (and `stoppedBy`/`doneBy` where stamped) ride the list projection like they ride the thread. |
| `GET /api/tasks` | `200 { navigation, page }` — the task-summary read model (#157): one summary per thread ROOT, present tense from the chain head, the run/job endpoints untouched (see [jobs.md](jobs.md)). `navigation` is the ORGANIZATION's — `counts: { running, review, past }` plus the running (max 3) and review (max 5) previews, newest first — and does not change with any page filter; `page: { items, nextCursor }` obeys them. `?state=attention\|running\|review\|past` (default `attention` — running and review at once; `400 BAD_TASK_STATE`), `?q=` (case-insensitive substring of the ROOT command, trimmed, ≤200 characters — `400 BAD_QUERY`), `?repo=` (exact `owner/name` under the create route's `BAD_REPO` rules), `?author=` (root author's login, case-insensitive, letters/digits/dashes, ≤100 characters — `400 BAD_AUTHOR`), `?sort=newest\|oldest` (`400 BAD_SORT`, default `newest`), `?limit=` (integer 1–50, default 30 — `400 BAD_LIMIT`), `?cursor=` (`400 BAD_CURSOR` for anything this endpoint did not mint for this exact query — the cursor binds a version, the sort and every normalized filter). Keyset pagination on `(activity_at, root_id)` — no OFFSET; `nextCursor` is null on the last page. The org is the credential's, never a query parameter; `503 JOBS_UNAVAILABLE` when the organization has no job board. Summaries carry no output, gates, runtime object or session ids. Since 036 a summary also carries the thread's PR wait when it has one: `waitReason` (the block's reason, "review" — null for a thread that never waited), `waitingSince` (when the wait started) and `waitTerminalReason` (why the wait ended — `pr closed`, `task stopped`, `task removed` — null while it is open). The read prefers the OPEN wait over a terminal one, so a waiting thread reads waiting and a finished wait reads what exhausted it. |
| `GET /api/repos` | `200 { repos, installation, meta }` — the caller's org's GitHub App installation's repositories, for the picker. Every member of the installation sees the full list — installation access is the boundary (#99). A failed refresh is **still a 200**, carrying the last good list and a named `meta.error`, for the reason `/api/stats` serves a stale cache: an empty picker and an unreachable GitHub look identical otherwise, and only one of them is somebody's fault. An empty list with no error is its own state — the App is installed nowhere — and the SPA renders a different sentence for it. |
| `GET /api/env` | `200 { org, workspace, repos }` — the caller's view of the runner environment, in all three scopes (`org` and `workspace` as var lists, `repos` grouped `{ owner, name, vars }`). **A secret's `value` is null for every caller, admin included** — the write-only echo; `isSecret` and `updatedAt` still travel, which is what the page renders "set" from. | `PUT /api/env/org` | `200 { vars }`. The body is the **whole** core list — replay-safe like every PUT here. Provisions the caller's directory if it does not exist, which is idempotent and covers `AUTH_MODE=none` (whose caller never passes through the OAuth callback) and any session predating the deploy. With no workspace root configured it answers `200 { root: null, repos: [], orphaned: [], executors: [] }` — **not** a 503: that is a configuration somebody chose, and the page says so rather than showing an error. | `PUT /api/workspace/repos` | `202 { repos }`. Clones run in the background — a request that waited for one would be killed by any proxy in front of it. `400 BAD_BODY`, `BAD_REPO_NAME` (a name that cannot be a directory), `REPO_NAME_CONFLICT` (two owners, one checkout directory), `TOO_MANY_REPOS`, `UNKNOWN_REPO` (outside what the caller's org's installation can see, so the clone could only 404); `409 WORKSPACE_DISABLED`. |
| `PUT /api/workspace/executors` | `200 { executors }`. The body is the **whole** executor list, the same whole-list-replace argument as the repos route — but `200`, not `202`, because nothing runs in the background; the rows are written before the response is sent. Renaming an executor is just this PUT under a new name; a task already stamped with the old name keeps it (`job.executor` is an audit record), and a later claim whose label no longer matches a row fails with an unresolved executor instead of silently switching runners. `config` is stored verbatim and validated structurally only: an object, a known `type`, unique path-segment-safe names, at most 10 per member. - **The job routes are registered only when `buildApp` is given a job store**, like the ingest
  routes. See [jobs.md](jobs.md) for the lease and fencing-token rules behind the `409`s.
- **The workspace routes are registered only when `buildApp` is given a `userRepos` store**, the
  same bargain. An absent workspace *root* is a different thing entirely and does not remove them:
  the routes still answer, and report that the feature is off.
- **`/api/repos` and `/api/workspace*` are walled by falling through `requirementFor`**, not by
  being listed anywhere. The default is the safe one, which is the property worth keeping — a new
  route is authenticated unless somebody deliberately opens it.


- **`meta.organization.mode` is a discriminant, never inferred from `available.length > 1`.** A
  directory user with one membership can be granted a second with no deploy; a control disabled by
  list length is right today by accident and silently wrong then.
- **`400 UNKNOWN_ORG` is checked before `parseRange` and before `ensureFresh()`.** The organization
  selects *which* data set is being ranged, so it is the more fundamental error, and a bad request
  must never be answered with a 202 the client then polls forever. Rejected rather than ignored, and
  the `BAD_RANGE` precedent understates the reason: an ignored range at least echoes in
  `meta.range` where a reader could notice, whereas an ignored `?org=` would echo
  `meta.organization.current` as the configured org and render one organization's figures under a
  heading the caller did not ask for. Once the store is partitioned, "trust the parameter" must
  never become a habit — the day auth lands, that habit is a cross-tenant read. Guarded by
  "reports the organization, not the range, when both are wrong", which is what pins the ordering.
- **`org` goes no further than the guard.** The service knows the only organization there is, and a
  parameter it ignores is worse than no parameter.
